# KR-21036 — "Faster Startup" warm-pool toggle for Omni Chatbot

**PR:** https://bitbucket.org/syncappinc/krista-global-catalog/pull-requests/2553
**Branch:** `feature/KR-21036` → `release/omni-chatbot`
**Extension version:** `3.0.3` (kSDK `1.0.126-sp2`, min appliance `3.6.2-sp3`)

## Summary

Adds an opt-in **Faster Startup** toggle (Behavior section of Integration Settings) that maintains a background warm pool of pre-authenticated guest users, so new chatbot opens skip the live login round-trip and feel near-instant. The warm-pool machinery already existed; this PR puts it behind an admin-controlled flag (off by default), wires the flag end-to-end, and fixes the auth-context and null-safety issues uncovered while gating it. Also includes a small unrelated fix (KR-21030) to stop browsers caching `launcher.js`.

## What changed

### 1. "Faster Startup" toggle (KR-21036)
- **UI** (`integration/index.html`): new checkbox **"Faster Startup"** in the **Behavior** section, persisted as the `createPoolUsers` UI-config field (populate + save wired).
- **Flag plumbing** (`ChatBotPool`, `ChatBotExtension`): `createPoolUsers` is parsed from the UI-config JSON and cached in memory (`createPoolUsersEnabled`), write-through on every UI-config update and on invoker load — no KVS reads on hot paths.
- **Pool fill is now gated on the flag:** refill / lazy-fill only runs when the toggle is on. When off, the background sweep (every 5 min) drains the pool via `deleteAllEntriesAsync()` (hard delete of pooled guest accounts).
- **Role-change reconciliation** is mutex'd so a Default-Role change reconciles existing entries in place without races.
- **`GET /authn/pool-entry` short-circuits to `204`** when the toggle is off — predictable response, no pop/log work, and safe against stale FE bundles / direct API hits.

### 2. Auth-context & null-safety fixes (uncovered by the gating work)
- **`saveUIConfig` now hands pool refill/drain to the sweep loop via `wakeSweep()`** instead of running inline. The Studio admin save request has an unauthenticated chatbot `AuthorizationContext` (no chatbot-session cookie), so inline KSDK calls failed with `MustAuthenticateException`/500. The sweep loop runs in the pool's construction-time thread-local context, which has working KSDK auth.
- **Null-safety guards across the auth pipeline** (`ChatBotAuthResource`): guard `AuthorizationContext`/`AuthenticationResponse`/`extras` against null so an unauthenticated or cookieless call no longer NPEs; fall through to fresh provisioning as before.
- Default-role resolution simplified (`AccountProvisioner.getDefaultRoleName`, `RoleUtils`); removed dead `BOOTSTRAP_DEFAULT_ROLE_KEY_PREFIX` constant.

### 3. launcher.js cache fix (KR-21030)
- `launcher.js` is now served `no-store` (was `public, max-age=1800`). It is per-invoker and must be fresh on every load. `launcher.css` keeps the 30-min cache.

### 4. Versioning & docs
- Extension bumped to **3.0.3**; kSDK dependency to **1.0.126-sp2**.
- `docs/pages/release-notes.md` updated with the 3.0.3 entry and upgrade notes (toggle behavior, hard-delete-on-disable caveat, Default-Role/View-access note).

## ⚠️ Operational notes for reviewers / release
- **Off by default** — no pool entries created until an admin enables and saves.
- **Disabling deletes pooled accounts on save (hard delete).** If a user is mid-chat when the toggle is turned off, their guest account is removed and their session ends abruptly — flip it off during a quiet window.
- The **Default Role** must have **View** access to the Welcome and Fallback conversations regardless of the toggle state.
