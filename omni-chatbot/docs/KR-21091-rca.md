# RCA & Fix — KR-21091: `config` API spike / `OPTIONS ... 499` during invoker upgrade

## Summary
During an invoker upgrade, the `/chatbot/config` API (and its CORS `OPTIONS` preflight) spiked with `499`s from live embeds (e.g. `adanielectricity.com`), while `launcher.js` / `launcher.css` did **not** spike. The chatbot failed to boot for users hitting the upgrade window.

## Symptom
- nginx logs during the upgrade window showed bursts of:
  `"OPTIONS /extension/api/<invokerId>/chatbot/config HTTP/1.1" 499`, with the preflight being **proxied to the upstream Extension Proxy** (`...:8765`) — not answered at the edge.
- Only `config` spiked; `launcher.js` / `launcher.css` were unaffected.

## Root cause
1. **An invoker upgrade briefly takes the Extension Proxy (EP) offline** (unload old → load new). Every EP-served endpoint `499`s during that window.
2. **`launcher.js` / `launcher.css` were shielded** — they are served as static objects from **AWS S3** (EP-independent), so they survived the upgrade.
3. **`config` had no such shield** — it is EP-served and was **not CDN-cached** (the iframe called the unversioned `/chatbot/config`, which no CloudFront behavior covered). Every active visitor's launcher *and* iframe re-hit the EP for config → the spike concentrated on `config`.
4. **A CORS preflight made it worse and user-visible.** The iframe's config `GET` sent `Content-Type: application/json` (and session headers when a session existed), all non-CORS-safelisted → the browser fired an `OPTIONS` preflight first. `OPTIONS` is proxied to the EP and is never CDN-cacheable; during the EP outage it `499`ed, and because the browser will not send the real `GET` until the preflight succeeds, **config never loaded → the chatbot failed to boot** for those users.

## Fix

### Frontend (`omni-angular`)
- `services/api.service.ts`: `get()` no longer sends `Content-Type` (bodyless GETs don't need it and it forced a preflight). Added `getPublic()` for user-independent, CDN-cacheable GETs — sends **only** `Accept` (no `Content-Type`, no session headers) → a CORS "simple" GET with **no preflight**. `getAuthenticatedHeaders(..., includeContentType, includeSessionHeaders)` gained the session-header toggle.
- `services/config-api.service.ts`: `config` and `supportedLanguages` are now fetched via `getPublic(toVersionedEndpoint(...))` → **versioned, preflight-free** URLs (`/chatbot/{v}/config`, `/chatbot/{v}/supportedLanguages`).
- `config/app.config.ts`: `getCdnCacheVersion()` resolves the server-injected `window.cdnCacheVersion` (falls back to `0` on localhost).

### Backend (extension)
- `service/ChatBotUIService.java`: `launcher.js` `Cache-Control` changed `no-store` → `public, max-age=1800, s-maxage=1800, stale-if-error=86400` so the **CDN can serve it** (replacing the manual S3 paste). URL unchanged (it is hard-coded in live customer pages).
- `contants/Constants.java`: `CACHE_PUBLIC_30MIN` gained `stale-if-error=86400` so the CDN serves the last-good copy while the EP is down (covers the upgrade window). Shared by config, supportedLanguages, launcher-file, launcher.css, index.html.
- `filter/CacheControlResponseFilter.java` (new, registered in `ChatBotApplication`): **default-deny** — stamps `Cache-Control: no-store` on any response without an explicit one, so a single generic CloudFront behavior caches only opted-in endpoints and can never cache a dynamic/auth endpoint by accident.
- `ChatBotExtension.java`: added invoker **lifecycle timing logs** (`onInvokerLoad` per-step + total, `onInvokerUnload`) to quantify the unavailability window and correlate with the 499 burst.

### Infra (CloudFront) — not code
- Keep `*/chatbot/*/ui/*`; add a generic **`*/chatbot/*`** behavior with an **honor-origin cache policy, Min TTL 0**, cache key = URL only (exclude `Authorization` / `Chatbot-Session-Id` / cookies). This caches config / supportedLanguages / launcher.js / launcher.css from origin and shields them during upgrades, while dynamic endpoints stay uncached via default-deny.
- Retire the manual S3 launcher paste (origin-through-CDN replaces it).

## Verification
- config / supportedLanguages now issue a plain `GET` (no `OPTIONS`) — eliminates the preflight `499` and halves config requests.
- With `stale-if-error` + the CDN behavior, config / launcher are edge-served (incl. stale) during an EP bounce → no origin spike; the chatbot bubble / boot survives the upgrade.

## Residual risk / follow-ups
- **Chat still depends on the EP.** `session`, `inboxes/*/messages`, and the WebSocket are user-specific / dynamic and cannot be cached, so the live conversation is still affected while the EP restarts. **Full chat resilience requires low/zero-downtime invoker upgrades** (rolling restart / warm replica) — recommend a separate platform ticket.
- The generic CloudFront behavior is only safe with **honor-origin + Min TTL 0** (a fixed-TTL policy would cache `no-store` responses — dangerous).
- `/authn/type` has no caller in this repo (possibly platform-consumed) — verify against `kristagrand` before any cleanup.
