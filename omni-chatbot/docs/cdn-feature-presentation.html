Keeping the Chatbot Alive During Server Upgrades

CDN Boot Resilience — how we make the chat bubble load on customer websites even while Krista is restarting.

KR-21091CDN caching / boot resilience
The Problem

Every upgrade made the chatbot vanish

Before What customers saw

  • We upgrade / restart an invoker (routine).
  • During that window the chatbot's config request has nowhere to go.
  • The bubble fails to load on the customer's live website.
  • Proxy logs flooded with 499 errors (browser gave up waiting).
Healthy
➜
During upgrade

A real production incident on a customer site (Adani) — the bubble disappeared every time we deployed.

Why It Happened

The browser asked the origin server …every single time

Customer
Browserneeds config to boot
→
Krista Originrestarting ✕

To draw the bubble, the browser first fetches /chatbot/config. That request went straight to the origin server on every page load. When the origin is down for an upgrade, the request times out → no bubble.

💡
Key insight: config rarely changes (it's just the bot's theme, logo, welcome text). There is no reason to ask a live server for it on every single visit.
The Idea

Put a CDN cache in front of the config

Customer
Browser
→
CDN Edge
(CloudFront)keeps a copy 30 min
→
Krista Originrestarting ✕

The CDN sits between the browser and the origin. Once it has a copy of the config, it can answer the browser itself — even when the origin behind it is down.

Think: a nearby shop with the item in stock… …so you don't drive to the faraway warehouse each time.

How It Works — 1 of 3

We tell each response how long it may be cached

WhatCache rule (plain English)Why
config, launcher-file, supportedLanguages Browser & CDN keep it 30 min; serve last-good for up to 24 h if origin is down Rarely changes; must survive upgrades
launcher.js / .css CDN keeps 30 min; browser always re-checks the edge Edge-served, but updates propagate fast
Hashed UI files /ui/… Cache 1 year (filename changes when content changes) Safe forever — new build = new name
Everything else
(messages, session, login)		 Never cached — default-deny Private, per-user data
🔒
Default-deny: anything that doesn't explicitly ask to be cached is stamped "do not store." Caching is opt-in, so private data can never leak into a shared cache by accident.

The version segment (/0/) is added by the app and removed by the server — backend routing is unchanged. When we ship a new config shape, we bump the number and the CDN naturally starts a fresh cache entry. No manual cache purge needed.

How It Works — 3 of 3

But admins must see edits instantly

The tension

  • Customers want cached config (fast, resilient).
  • Admins previewing changes want fresh config (no 30-min wait).

Same data, two opposite needs.

The solution — a separate door

Customers → /config  (cached 30 min) Preview → /config/preview  (never cached)

"Try It Live" flips a preview flag → the chatbot fetches the uncached door. Admins see saved changes immediately; customers keep the fast cached path.

🚪
A separate URL path (not a query parameter) — because CDNs may ignore query strings when caching, which would silently serve the stale copy.
Safety First

What is cached — and what is never touched

✓ Safe to cache

  • Config — bot theme, logo, welcome text
  • Launcher scripts & styles
  • Hashed UI asset files

All public, user-independent data.

✕ Never cached

  • Chat messages
  • Session & authentication
  • Anything user-specific

Guaranteed by the default-deny rule — no accidental exposure.

One Thing DevOps Must Set

CloudFront must obey our rules Min TTL = 0, Default TTL = 0

Our code sends the correct instructions — but the CDN only honors them if it's configured to. Two traps if it isn't:

Min TTL > 0

CloudFront caches for at least that long even when we say "never cache." Private messages could get stored → one guest could see another's chat.

Default TTL > 0

Applies to responses with no cache header. Older invoker versions send none on messages/session → their responses could get cached.

✅
Both = 0: "never cache" is honored, header-less responses stay private, and our opt-in cacheable endpoints still cache normally. Go-live gate.
